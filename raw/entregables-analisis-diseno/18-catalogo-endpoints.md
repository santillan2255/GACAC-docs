# Catálogo de endpoints de la API

Artefacto 7.1 del índice de entregables, complemento de [`18-contratos-api.md`](18-contratos-api.md). Responde, para cada API y cada endpoint, **para qué sirve, qué hace, quién lo usa, qué recibe y qué devuelve**, en lenguaje de negocio. Los contratos técnicos están en `18-openapi/` y se navegan en el [visor Swagger](18-swagger/index.html), que muestra la misma ficha en cada operación.

Generado el 05-11-2026 con `_trabajo/gen_18_catalogo_endpoints.py` (textos de `_trabajo/endpoints_lib.py`). No se edita a mano: tras regenerar `18-openapi/`, se ejecutan este script y `_trabajo/gen_swagger.py`.

## Cómo está organizada la API

Hay **una API por módulo** (anexo de la especificación) y una **API externa** para terceros. Dentro de cada API los endpoints se agrupan por función (las subsecciones del §11 del anexo: backoffice, portal, campo, etc.). El primer segmento de la ruta dice quién la usa:

| Prefijo de ruta | Quién la usa |
|---|---|
| `/api/admin/<mod>/...` | Personal de la cooperativa, desde el backoffice |
| `/api/por/...`, `/api/portal/...`, `/api/me/...`, `/api/<mod>/my/...` | Socio, desde el portal y la app de autogestión |
| `/api/field/...`, `/api/<mod>/collector/...` | Personal de campo y cobradores, desde la app móvil |
| `/api/platform/...` | Equipo de GoodApps, desde la consola de plataforma (todos los tenants) |
| `/api/public/{tenantSlug}/...`, `/l/...` | Cualquier persona, sin iniciar sesión |
| `/api/auth/...` | Inicio y administración de sesión |
| `/api/v1/ext/...` | Sistemas de terceros con credenciales de cliente |
| `/api/internal/...`, `/health`, `/readyz` | Uso interno y monitoreo |

## Cómo leer cada ficha

Cada endpoint tiene una ficha con estos datos:

| Dato | De dónde sale |
|---|---|
| **Qué hace** | La descripción de la fila API del anexo (§11), seguida de una frase armada con el método HTTP, la forma de la ruta y el nombre de la colección en T05. |
| **Para qué sirve** | El requisito funcional (RF) que el endpoint implementa, con su texto del §5 del anexo. Si la fila API o el anexo lo vinculan, se cita tal cual. Si no, se elige el RF del anexo con más palabras en común y se marca *a confirmar*. |
| **Quién lo usa** | El canal, según el prefijo de la ruta (backoffice, portal del socio, app de campo, consola de plataforma, terceros, público), y el permiso (capability) de T02. |
| **Recibe / Devuelve** | Parámetros, cuerpo y respuesta exitosa del contrato OpenAPI. |
| **Pantallas** | Pantallas del catálogo 4.5 que exigen el mismo permiso. |
| **Ola y fuente** | Ola de construcción y línea de la fila API en el anexo. |

## Limitaciones

- **Descripciones breves en el anexo.** Muchas filas API describen el endpoint con dos o tres palabras ("Maestros", "RMA"). La frase de "Qué hace" las completa con el método, la ruta y la colección, pero no agrega reglas que el anexo no dice.
- **Respuestas sin estructura.** 1.762 endpoints (42,0 %) devuelven un resultado genérico porque el anexo no define su estructura (acciones, tableros, simulaciones); se precisa en el diseño detallado de cada ola.
- **Vínculo con requisitos.** Los anexos casi nunca vinculan API con RF. El vínculo inferido acierta en la mayoría de los casos revisados por muestra, pero no siempre: hay que confirmarlo con el anexo antes de construir.
- **Pantallas.** Se vinculan por permiso; una pantalla puede usar endpoints con otro permiso (por ejemplo, lecturas de otro módulo) que no aparecen en la ficha.
